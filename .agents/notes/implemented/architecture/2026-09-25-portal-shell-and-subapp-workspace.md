# Agent Note: 门户外壳极简化与子应用全屏工作区

Status: implemented

Scope: apps/portal/src/shell/**,apps/portal/src/router/**,apps/portal/src/styles.css

Last-verified: 2026-09-25

## Problem

负责人提出两条被现有实现同时违反的要求：

1. 「点击子应用打开的弹窗/位置居然是组件内嵌页面，这是很忌讳的 UX 设计」——点「打开应用」后，子应用的内容会出现在门户框架**内部**：门户外壳（品牌头、页面标题、披露条、底部导航）一直包着它。这意味着子应用永远只能拿到「视口减去门户外壳」这块残缺的画布，门户的导航还会和子应用自己的导航打架。
2. 「菜单、导航栏设计布局也很糟糕，和钉钉工作台风格一点也不像，外框架应该极具紧凑感信息密度高占位小」——此时门户的框架是「大标题 + 说明 + 40px 外边距的页头」「卡片式披露条」「悬浮胶囊底部导航」三层叠加，首屏顶部就被吃掉一百多像素。

两条要求指向同一个根因：**门户外壳把自己当成了主体，而不是给子应用让位的容器**。

同时，原实现里「打开应用」按钮是永久禁用的，并且有一条测试把它锁成不变量（点击后 `pathname` 必须不变）。那条不变量在当时是对的——没有子应用容器，能点却打不开才是更大的问题——但它和「要有一个真正的子应用入口」直接冲突。

## Decision

### 门户外壳：40px 单行顶栏 + 28px 标题行，没有页头、没有页脚

`PortalShell.tsx` 重写为三段：

- **40px 顶栏**（`.ui-appbar`，宽屏 48px）：品牌（20px 图标 + 「AI 中台」，无 slogan）→ `<nav aria-label="主导航">` → 组织名 + 头像。品牌从「两行带副标题」压成一行，因为 40px 放不下两行，副标题挪到登录页去讲。
- **28px 标题行**（`.portal-titlebar`）：左边 `h1` 是当前页名，右边是体验披露条，两者共用一行。这保住了「每页恰好一个 h1」与「`role="note"` 持续在场」两条被测试锁住的语义，又不再为它们各开一行。
- **内容区**，无 `.ui-footnote`、无页面页头。

导航在**同一个 `<nav>` 里**按断点二选一：宽屏是横向文字导航（当前项 2px 品牌色下划线），窄屏是顶栏内的紧凑「图标 + 文字」横排。**不设底部导航栏**——窄屏顶栏只有 40px，竖排两行的图标+文字会被压到重叠；横排一行放得下，且导航与内容之间不再多一条固定浮层遮挡。原先为底部导航预留的 `--ui-tabbar-h` / `--ui-z-tabbar` 令牌已随之删除。

### 顶栏的高度是框架契约，不是内容的结果

`display: flex` 与 `min-height: var(--ui-appbar-h)` 两件事**必须成对出现**，而且不能只写在应用内部容器上。

这个坑真实发生过：重构中 `.portal-appbar__inner` 只写了 `gap` 而漏了 `display: flex`，于是品牌（inline-flex）、导航（块级）、身份区（inline-flex）各自成为一行，顶栏实测高度从 40px 变成 **95px**（≈ 三者高度之和）。页面不报错、测试不红、也不产生任何重叠或裁切，肉眼只觉得「顶栏有点高」。定位它靠的是 `node scripts/qc/css-probe.mjs <url> .ui-appbar 1440 height` 打出来的盒子树。

因此现在把这层保险放在两处：

- `.ui-appbar`（共享层）自己带 `display: flex` + `min-height: var(--ui-appbar-h)`——**框架的高度归框架**，任何一个应用忘了给内部容器写 flex，顶栏至少不会纵向堆叠；
- 应用内部容器（`.portal-appbar__inner`）负责版心与横向间距，并同样声明 `min-height`。

另外 `.portal-nav` 必须 `align-self: stretch`：顶栏是 `align-items: center` 的，导航块默认只占内容高度，那样当前项的下划线（`bottom: 0`）会飘在文字下方而不是贴在顶栏底边。

审计已补上对应的机械检查（「外框元素的实际高度不得超过它自己声明的 `min-height` + 4px」），见[版式审计笔记](../testing/2026-09-25-layout-audit-in-real-browser.md) 的「外框占用检查」一节——它同时抓到了后台顶栏在手机上的 85px 与 45px 两处同类缺陷。

### 子应用工作区：路由挂在门户外壳之外

`PortalRoutes.tsx` 里 `/apps/:appId/*` 是 `PortalShell` 父路由的**兄弟**，不是它的子路由：

```
<Route element={<PortalShell />}>    ← 工作台 / 应用市场 / 功能进展 / 登录
<Route path="/apps/:appId/*" element={<SubAppWorkspace />} />   ← 全屏接管
```

这样工作区渲染时门户外壳**根本没有挂载**，不存在「靠 CSS 藏起来」的可能——没有 DOM，就没有样式能把它露出来。

`SubAppWorkspace.tsx` 给出一条 36px 的工作区条（返回 + 子应用名 + 分类），其余高度全归 `.workspace__stage`。这是本轮能做到的最小干扰：门户只留一条细条，子应用拿到的画布是视口减去 36px。

### 「打开应用」从禁用改为真实入口

`AppDetailDrawer` 的「打开应用」现在 `navigate('/apps/' + appId)`。相应的保护性质换了一条而没有被放弃：测试从「点击后 `pathname` 不变」改为「点击后进入 `/apps/ai-image-gen`，且该页面上**没有任何门户导航**（`queryByRole('navigation', { name: '主导航' })` 必须为 null）」。断言的对象从「进不去」变成「进去之后门户框架确实不在场」——后者才是这条要求真正的含义。

## 容器当前是占位，不是集成

`/apps/:appId` 现在渲染的是一块**占位**：标题、一句「还没有接入这里」、一个返回工作台的出口。它不发任何网络请求、不挂 iframe、没有任何 `src`。

这是刻意的。真实子应用由 P0-4 的容器适配层注入，本轮只解决「门户不再把子应用镶进自己肚子里」这个结构问题。把占位说成集成会让下一轮的人以为这里已经接好了。

## Alternatives considered

### Why not 保留门户外壳，用全屏遮罩把子应用盖在上面？

实现上最省事：不改路由，子应用容器 `position: fixed; inset: 0` 盖住一切。否掉的原因是这样**门户外壳仍然在 DOM 里**：它继续运行（`useRouteMeta`、`matchMedia` 监听、导航的 `aria-current` 都在算），键盘 Tab 顺序会走到被盖住的导航上，读屏软件读到的仍是一个「外壳 + 子应用」的复合页面。视觉上盖住了，语义上没有。把路由挪到外面则是从结构上消除这个问题。

### Why not 窄屏保留底部导航栏（钉钉工作台就是底部 TabBar）？

钉钉工作台确实有底部 TabBar，从「像钉钉」的角度这是最直接的答案。否掉的原因与本次的密度目标冲突：底栏要占 52px 且必须固定悬浮，于是内容区上下各被切一刀；而窄屏顶栏只有 40px，「图标在上、文字在下」的两行导航塞不进去，只能把它做成浮层——浮层正是负责人点名批评的东西。

作为补偿，窄屏顶栏的导航项保留了图标与文字（横排），识别性没有降级，并且两个断点下的导航都是 `<Link>`，键盘行为、`aria-current`、「新标签打开」能力一致。

### Why not 直接让「打开应用」继续禁用，等真实容器就绪再开放？

这是最保守的选择，也保住了原有的测试。否掉的原因是这样会让这一轮的结构改动无法被验证：路由是否真的挂在外壳之外、外壳是否真的不再挂载，只有走通这条路径才能确认。先有占位再填实现，占位本身也是一个可被断言的对象。

## Consequences

**收益**

- 子应用拿到完整画布。这是本次改动的核心收益，也是后面所有子应用接入工作的前提。
- 门户框架从「三层叠加约 200px」压到「40px + 28px」。首屏留给内容的面积明显变大。
- 窄屏与宽屏的导航是同一份 DOM 结构下的两种排布，不是两份实现；导航语义（`<Link>`、`aria-current`、`aria-label="主导航"`）在两种形态下一致。

**代价**

- `AppDetailDrawer` 不再是组件库的 `Drawer`，改成自绘的 `.overlay` 面板（遮罩 + 焦点陷阱 + Escape 关闭 + 打开时焦点进面板、关闭时焦点还原），并且**用 `createPortal` 挂进 `document.body`**。自绘的代价是要自己补齐这些无障碍行为；组件库的 `Drawer` 在窄屏会渲染成底部抽屉，而这里希望两种断点下都是「盖住整页的遮罩 + 居中/贴底面板」，所以换掉了。
- **浮层必须 portal，这不是洁癖是地雷排**：`.portal-content` 带着 `ui-enter` 入场动画，而 `animation-fill-mode: both` 会把 to 帧永久留在元素上——Chrome 把动画过的 `transform: none` 计算成**单位矩阵** `matrix(1,0,0,1,0,0)`，按规范它照样让元素成为 fixed 后代的包含块 + 层叠上下文。后果（状态审计实测）：浮层矩形是 `100,101,1240,490`（内容盒）而不是视口，`z-index:1000` 被关进局部上下文，被 `z-index:100` 的顶栏压住，关闭按钮点不到——**全部测试绿、几何审计零报告**，因为只有它的悬停/点击被挡死了。两道修复：① 浮层 portal 进 body（浮层天生该在 body 层）；② `ui-enter` 改成纯 opacity 动画（不留 transform 尾巴），带位移的入场曲线移到 `.ui-rise`，只准用在「下面不会有 fixed 后代」的叶子上（浮层面板、兜底卡）。
- 浮层里有两个关闭入口（标题栏图标、底部文字按钮），这是刻意的双入口，但意味着按可访问名「关闭」查询会命中两个——测试必须限定在 `.overlay__foot` 里查。
- 「打开应用必须保持禁用」这条旧不变量在本次被取代。若将来有人重新启用它，需要同时改回 `App.test.tsx` 里的两条断言（工作区可达、工作区内无门户导航）。
