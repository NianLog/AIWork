# Agent Note: 界面文案改为业务语言，演示态披露统一措辞

Status: implemented

Scope: apps/portal/src/**,apps/admin/src/**

Last-verified: 2026-09-25

## Problem

重构前的界面把工程内部口径直接摊给了终端用户：导航与标题里出现「P0-1 工程骨架」「micro-app 容器」「OpenResty 网关」「MinIO 静态包」「Yudao Cloud 身份服务」「RBAC」这类表述，演示态提示写的是「工程预览（非登录态）」「不包含业务数据」。

这些词对写代码的人有信息量，对使用门户的业务成员没有——他们不知道 micro-app 是什么，也不需要知道。「看不懂的表述等于没有表述」，更糟的是它会让界面显得不可信：一个连自己说什么都说不清楚的系统，很难让人相信它能管好应用与权限。

演示态披露还有第二重问题。它同时承担两个安全职责：说明数据是假的、说明当前没有登录态。用内部术语写披露，等于把安全语义藏在黑话里——用户看不懂就不会当真，而这条提示的全部价值就在于被当真。

## Decision

- 全部面向用户的文案改为业务语言：导航、页面标题、表单标签、按钮、空态、错误页、披露提示，无一例外。开发者注释与代码标识符不受此约束，它们本来就不渲染。
- 内部标识 never 渲染到界面：角色编码（`platform:admin`）、记录主键（`r-01`）、权限码（`ai-image-gen:task:create`）都只存在于 `store/` 的数据里。角色页只展示角色名称、数据范围与数量。
- 演示态披露两端同值：`DEMO_DISCLOSURE = '体验示例 · 非真实数据'`。门户持于 `apps/portal/src/store/demoCatalog.ts`，后台持于 `apps/admin/src/store/demoDirectory.ts`，两处 must 在同一 PR 内同步修改（文件内已有注释约束）。
- 披露 must 以 `role="note"` 持续在场，不只出现在登录页；后台额外附一段 `DEMO_EXPLANATION` 说明「数据从哪来、为什么保存不了」。
- 术语约束由测试机械执行，不靠评审肉眼：两端测试各持一份 `ENGINEERING_TERMS` 清单，断言 `document.body.textContent` 不含其中任何一项；后台另有 `INTERNAL_IDENTIFIERS` 清单。执行方式见[测试笔记](../testing/2026-09-25-vitest-dingtalk-esm-and-semantic-tests.md)。

## 术语映射表

这是跨两端的翻译契约。内部口径变化时，界面文案与测试常量要同批改，漏一处测试就红——这是有意设计的摩擦。

| 内部说法 | 界面说法 |
| --- | --- |
| `stable` / `canary` / `paused` | 正式版 / 试运行 / 已停用 |
| 接入状态 | 功能进展 |
| 工程预览（非登录态） | 界面功能体验；入口写「无需登录，先看看界面」 |
| 身份服务未接入 | 统一登录尚未开通 |
| 注册与发布 / 提交注册 | 应用发布 / 提交上架 |
| 校验清单 | 检查内容 |
| 本地演示环境 | 体验环境 |
| RBAC / 权限点 | 角色 /「这个应用能做什么」 |
| 沙箱测试组织 | 临时协作组 |

映射不是逐词替换。「接入状态」改成「功能进展」是因为用户关心的是「这个能力现在能不能用」，而不是「这个系统接到哪一步了」；「校验清单」改成「检查内容」同理。

## Alternatives considered

### Why not 只改最刺眼的几个词？

成本最低，而且 P0-1、micro-app 这类词确实是最扎眼的。但术语不是零散污染，是一整套内部视角：留着「注册与发布」「校验清单」，用户仍然要在脑子里做一次翻译。而且局部替换无法机械验收——「改干净了没有」只能靠人逐页读，下一轮加页面时又会漏。全量替换配合术语缺席断言，才把这件事变成一次性且可守住的。

### Why not 把演示数据整体撤掉，界面只留空态？

这是更彻底的做法：没有假数据就没有「被误当成真」的风险，披露提示也可以简化。否掉的原因是它让界面失去验收价值——负责人要看的是「目标场景里这个后台长什么样」，五个空表格回答不了这个问题，也没法判断信息密度与层级是否合理。取而代之的是把只读约束做实：所有写意图按钮永久禁用且点击无效，演示 entry 与 backendApi 全部落在 RFC 2606 保留域 `.invalid`，界面上不存在任何指向它们的链接。风险由「不展示」改为「展示了但拿不走」，这两条都有测试锁着。

### Why not 把 DEMO_DISCLOSURE 提到共享包里让两端 import 同一份？

能消掉「两处常量靠注释同步」这个缺口，看起来是纯正的收益。但 `packages/shared-types` 是子应用与宿主之间的接口契约包（应用清单、权限码、网关头、五原语），把 UI 文案塞进去会让契约包承担展示职责，而契约包的稳定性要求比文案高得多——文案改一个字不该惊动子应用接入方。更关键的是这两个 `store/` 文件本身就是「接真实服务时整模块删除」的临时物，披露常量跟着它一起消亡才是对的归宿；提到共享包反而会让它比它所属的演示态活得更久。

## Consequences

**收益**

- 业务成员能直接读懂界面在说什么，不需要旁人解释。
- 术语缺席是机械断言，新增页面若带回工程黑话，测试当场就红。
- 披露文案的安全语义（数据是假的、没有登录态、保存不了）用大白话讲清楚了，被当真的概率高于黑话版本。

**代价**

- 术语映射表是人工维护的双向翻译，内部口径每变一次就要同步界面文案与测试常量。
- 两份 `DEMO_DISCLOSURE` 常量只靠注释约定同步，没有机械校验。这是一个明确的、被有意接受的缺口——理由见上面第三个备选方案。
- 部分表述变长了。「注册与发布」→「应用发布」、「校验清单」→「检查内容」尚可，但披露段落为了讲清楚安全语义明显比原来长，在窄屏上占位更多。

**缺口**

- `ENGINEERING_TERMS` 只覆盖已知词。新引入的工程黑话（比如某天有人写了「灰度维度」）不会被自动拦截，需要评审时人工加进清单。清单会随时间变长，这是它的正常工作方式，不是缺陷。
- 术语检查只读 `document.body.textContent`，因此属性值（`placeholder`、`aria-label`、`title`）与 `index.html` 的 `<title>` / `<meta name="description">` 都不在覆盖面内。本轮这几处已人工核过，但没有机械保障。
