# AI 中台生产级路线图（ROADMAP）

- 制定日期：2026-09-28
- 目标（用户拍板）：系统完全达到企业生产级验收标准——安全、性能、易用性、稳定性、高并发承载能力均完全可靠，无冗余代码和潜在漏洞。
- 本文把该目标翻译成**可验收的工程语言**，按批次排期。每批次有明确出口线，做完一条勾一条。

## 0. 验收哲学（先对齐认知）

两个目标需要重新表述，否则无法验收：

1. **「无潜在漏洞」不是终点态，是过程态。** 工程上可达的定义：*已知漏洞清零 + 持续审计机制在运行*（依赖审计进 CI、安全自查清单定期过、新代码过安全评审）。任何声称「绝对无漏洞」的系统都只是没测过。
2. **「高并发完全可靠」受架构天花板约束。** 当前是单实例后端 + 单 MySQL + 宝塔 GUI 运维。第一步不是加机器，是**测出真实容量数字**（批次 M），再按数据决定投入。盲目扩容是花钱买心理安慰。

排序总原则：**上线阻塞项 → 可观测性 → 安全收尾 → 性能基线 → 稳定性演练 → 代码质量 → 水平扩展（数据触发）**。测不准的系统调不了优，所以可观测性排在性能前面。

## 2. 批次规划

### 批次 J：上线基线（上线前必须完成）

用户已定：TLS 收紧推迟到上线时操作。本批次是上线 checklist，不写新代码：

1. **TLS**：宝塔面板 → aiwork.jbslab.cn → SSL → 只留 TLSv1.2/1.3，保存后 `curl -Iv` 复核；仓库 conf 镜像同步（`gateway.include.conf` 的 `ssl_protocols` 行）。
2. **凭据**：admin 换正式密码（面板 MySQL 改 `system_users` 或后台改密）；gwtest 试用期确认；网关 secret 与 MySQL root 密码轮换预案写 DEPLOY.md（不进 git）。
3. **备份**：宝塔 MySQL 定时备份（每日全量，保留 7 份）+ `mfe-storage` 目录纳入备份计划。
4. **配置核对**：compose 卷挂载、multipart 上限、`PORTAL_MFE_STORAGE_PATH`、tenant ignore-tables 与生产 compose 参数一致性过一遍。
5. **出口线**：TLS 检测工具（sslscan 或在线检测）≥ A；备份目录里有一次真实备份文件；DEPLOY.md 更新反映以上全部。

### 批次 K：可观测性（测不准就调不了）

1. 后端接入 `/actuator/health`（已有依赖则暴露），宝塔面板监控或 UptimeKuma 探活 + 告警（企业微信/邮件）。
2. 慢查询：MySQL `slow_query_log = ON`（long_query_time = 0.5s），每周看一次报告。
3. 访问日志聚合：nginx access_log 已有，补按状态码维度的简单统计脚本（面板计划任务跑）。
4. 错误可追溯：后端 log.error 带上下文（已有 uploadPackage 先例），统一 error 日志格式约定写 DEPLOY.md。
5. **出口线**：后端挂掉 60s 内有告警到达；能答出「上周 5xx 有几次、最慢的三个接口是什么」。

### 批次 L：安全收尾

1. **登录限流**：yudao 框架自带 captcha/限流能力排查（`yudao.security` 配置面），登录失败 N 次锁定或验证码，配置级优先于写代码。
2. **依赖审计进 CI**：GitHub Actions 加 `pnpm audit --audit-level high` 步骤（白名单豁免已 triage 的条目，与 DDE 笔记关联）。
3. **IDOR 自查**：按 security-and-hardening 清单过一遍全部端点的对象级授权（当前端点都带 @PreAuthorize 且对象按 appId 隔离，预期干净，复核留档）。
4. **会话策略**：accessToken 有效期/refresh 窗口/并发会话数核对业务预期，写进笔记。
5. **出口线**：CI 上 audit 门禁生效；暴力破解登录被限流（手工验证）；自查表落 DDE 笔记。

### 批次 M：性能与容量基线（拿数字）

1. k6（或 vegeta）压测四条关键路径：登录、enabled-list、子应用静态资源直出、上传。
2. 调优只做数据支持的：HikariCP 池大小（默认 10 起评）、Tomcat 线程、MySQL `innodb_buffer_pool`（宝塔 my.cnf）。
3. 慢 SQL 治理：批次 K 的慢查询日志里 Top 5 逐条加索引或改写。
4. 产出《容量基线报告》：单实例 RPS（四路径各自的 P99 延迟与极限）、瓶颈定位、扩容触发线（利用率 70%）。
5. **出口线**：报告落 `docs/`；「当前架构能扛多少并发」有数字可答。

### 批次 N：稳定性演练（不是加功能，是做实验）

1. **故障注入**：kill 后端容器 → 验证网关 5xx 降级页面与恢复；断 MySQL → 上传/登录失败文案不泄露内部细节；磁盘满 → 上传失败路径。
2. **备份恢复实操**：拿批次 J 的备份在本地真实恢复一次（恢复没验证过的备份等于没有备份）。
3. **优雅停机**：滚动重启时上传中的请求不产生孤儿目录（事务+删目录逻辑验证）。
4. **出口线**：三个演练各留一份记录（现象/恢复时间/发现的问题清单）。

### 批次 O：代码质量与工具链

1. 工具链升级：vite 5→6、vitest 2→4、react-router 6→7（三条独立小批次，各自全量 verify + e2e 抽查）。react-router 7 升级后可回看 CVE-2025-68470 是否仍需防御过滤（保留也不亏，纵深防御）。
2. 死代码盘点：knip 或 ts-prune 跑一遍，人工确认后清理。**放在真实使用一段时间后做**——现在删「没人用的代码」容易删到「还没人用的新功能」。
3. 重复模式收敛：仅当评审或维护中实际踩到重复痛点才做，不为抽象而抽象。
4. **出口线**：三条 major 升级各自 PR 合并且 CI 绿；knip 报告清零或豁免留档。

### 批次 P：水平扩展（触发条件驱动，不预先做）

**触发条件：批次 M 的容量数字利用率达 70%**（如压测极限 500 RPS，业务量到 350 RPS）。届时按序：

1. 后端多实例 + nginx upstream 负载均衡（上传目录已是共享卷前提，需挪到两实例都挂的路径或对象存储）。
2. Redis 权限缓存从 5s TTL 调长 + 主动失效（撤权实时性当前靠 5s 过期，多实例下改 Redis 广播失效）。
3. MySQL 读写分离（先从库只读给 enabled-list 这类读多的端点）。
4. 上传大文件走 OSS/COS 直传（本地磁盘释放）。

**拒绝清单**（现在不做，写明为什么）：
- 微服务拆分——当前一个模块、单团队、无独立扩缩需求，拆分只增加运维面。
- 多租户 SaaS 化——业务没有这个需求信号。
- K8s——宝塔单机规模用不上，运维复杂度不匹配。
